# 三层十二问 · 功能闭环审计方法论

> **通用版(2026-08-08 抽象)**: 从 MengPaw #1 插件系统、#2 GitHub 连接两轮深度审计中提炼, 原版曾于 v0.24.0 清理, 现恢复并抽象为项目无关的方法论。
> 适用于**任何"Agent 能否自主完成一个功能闭环"**的审查: 插件系统、会话管理、记忆孪生、触发器、进化系统、外部集成……
> 互补关系: 本方法问**闭环是否完整**; 金字塔彻查法(pyramid-investigation.md)问**现象为什么发生**; 九维审查(code-review)问**代码写得好不好**; 功能审计清单(methodology.md)问**实现有没有坑**。
> **v0.47.x 扩展 (命令退役整改)**: 三层各加一问 — 1.7 幽灵引用 / 2.7 双通道语法一致性 / 3.7 保护链路判定表命中率。这三问来自一次真实事故: 46 条命令被删后, 提示词、技能手册、任务脚本、错误文案、安全判定表仍指向它们, 而守护测试只覆盖了 1 个文件 + 4 个命名空间。**结论: 没有守护测试的"渠道"必然腐化** —— 每条渠道都要有对应的静态扫描测试。

## 核心信念

一个功能"Agent 能用", 不是代码跑通了就算, 而是**从 Agent 认知到落地执行到外部依赖全链路闭环**。三层各管一段, 任何一层断, 功能就"代码存在但 Agent 无法自主完成"——这是框架类项目最常见的隐性缺陷(代码存在 ≠ Agent 可触达)。

## 三层十二问

任何功能闭环必须在这三个维度上经得起追问:

### 1. Agent 认知层 — "Agent 是不是这个领域的专家?"

| # | 问题 | 检查要点 |
|---|------|---------|
| 1.1 | Agent 知道这个功能的存在吗? | 系统提示词有没有提及?有没有 Few-shot 示例? |
| 1.2 | Agent 知道从哪里获取资源吗? | 下载源、存储目录、配置入口是否在提示词中明确? |
| 1.3 | Agent 知道用什么命令操作吗? | 命令手册 / 工具列表是否覆盖?命令返回格式是否 LLM 友好? |
| 1.4 | Agent 知道功能的简介/描述吗? | 列表命令是否附带 description?搜索命令是否可发现? |
| 1.5 | 操作成功后 Agent 得到指引了吗? | 成功结果是否回传真实内容/下一步动作?是否有技能可查阅? |
| 1.6 | Agent 有合理的权限边界吗? | 哪些操作不该允许?删除/卸载有无保护?依赖检查? |
| 1.7 | **Agent 读到的指令还成立吗?** | 提示词 / 技能文档 / 工作区模板 / 错误文案里教的命令是否仍然存在?有没有指向已删命令、已退役插件、已移除文件的**幽灵引用**? (v0.47.x 新增 — 实测 49 处 A 类幽灵引用, 系统提示词曾指向一整篇教已删命令的手册) |

### 2. 软件逻辑层 — "代码和 UI 是否支撑闭环?"

| # | 问题 | 检查要点 |
|---|------|---------|
| 2.1 | 有固定、独立的存储目录吗? | 目录是否可预测?Agent 能否用文件系统命令访问? |
| 2.2 | Agent 能否验证状态? | 有无 verify/size/stat 命令?能否区分"安装成功"和"文件丢失"? |
| 2.3 | UI 是否提供操作反馈? | 进度百分比(真实值)?成功/失败提示?状态徽标? |
| 2.4 | 操作后是否自动注册/生效? | install → activate → 命令可用, 是否一气呵成? |
| 2.5 | 提供"彻底删除"和"临时禁用"两种粒度吗? | 删除清数据 + 禁用只停功能?入口是否区分? |
| 2.6 | 异常路径有处理吗? | 失败有重试?错误有引导?数据损坏有恢复?声称成功有真实依据? |
| 2.7 | **两条通道对同一语法是否一致?** | 框架命令通道与 Linux 命令通道对同一参数形态 (`-n` 单横线选项、引号、重定向) 解析结果是否相同?安全层放行的语法, 执行层是否也放行? (v0.47.x 新增 — CommandMonitor 放行 `grep -n`, 而 CliInterpreter+Pipeline 把它静默改写成 `--n` 并挪走位置参数) |

### 3. 服务/基础设施层 — "外部依赖是否可靠?"

| # | 问题 | 检查要点 |
|---|------|---------|
| 3.1 | 主要外部依赖有备份吗? | 主源挂了有镜像?单点故障? |
| 3.2 | 失败时是否告知替代方案? | 错误消息含建议吗(检查网络/换源/重试)? |
| 3.3 | 版本/更新信息是否传递给 Agent? | 版本号比较 + changelog + 升级路径是否完整? |
| 3.4 | 网络受限场景是否告知 Agent? | 提示词 + 错误消息 + 工具命令三通道覆盖? |
| 3.5 | 数据完整性有保障吗? | 校验和?原子写入?统计指标是否持久化(重启不丢)?损坏自动恢复? |
| 3.6 | 降级路径是否自动化? | 自动切换/缓存兜底?无需用户手动干预? |
| 3.7 | **保护链路的判定表还命中吗?** | 安全表 (风险分级/高危/白名单/路径保护) 里的每一项是否仍对应真实存在的命令或真实路径?判定入口是否在**所有**执行通道上都被调用? (v0.47.x 新增 — 路径保护只挂在 Pipeline, Linux 通道写操作零拦截; 且 Vault 前缀写错 applicationId 双重失效) |

## 使用方法

1. **选一个子系统**(如会话管理、进化系统、插件市场)
2. **逐条过**: 对每一条回答"是 / 否 / 部分 / N/A"
3. **标记缺口**: 否和部分的项目就是待修复的 Bug 或待实现的功能
4. **P0/P1/P2 分级**:
   - P0 = Agent 无法自主完成操作 / 数据丢失风险 / 用户无感知
   - P1 = 功能可用但体验差 / 缺少便利工具 / 无容错
   - P2 = 锦上添花 / 低频场景 / 可后续迭代
5. **按优先级施工**, 修复后重跑一遍十二问确认闭环

## 使用纪律

- **每次大功能落地后**用十二问过一遍, 不要等自检报告暴露
- **N/A 要显式标注**, 防止下次审查重复盘问
- **证据要 file:line**: 每个"是"都要能指出代码位置, 不许"感觉可用"
- **缺口要进缺陷清单**: 十二问发现的缺口 = 待办, 不是"知道了就行"
- **1.7 必查守护覆盖**: 任何"某渠道无测试守护"的结论都是 P0 候选 —— 没有守护的渠道必然腐化(v0.47.x 教训)

### #4 命令退役整改(v0.47.x, 新增三问的来源案例)

> 触发: 用户实测 Agent 查询公众号文章时连环失败 — tavily.extract 报语法错、声称 net.curl 不存在、
> skill.run browser-spider 重试无效、grep -n / wc -c 参数被"吞掉"。彻查后定性: 3 条是模型幻觉,
> 1 条是真框架缺陷, 且暴露了 v0.36.x「命令去重」遗留的系统性腐烂。

| 问 | 结论 | 证据 |
|---|------|------|
| 1.7 幽灵引用 | ❌ **49 处 A 类** — 系统提示词指向整篇教已删 `fs.*` 的 filesystem.md; 浏览器提炼任务脚本三步全用已删命令; `hermes.*` 全篇命名空间错位(真实为 `tribe.hermes.*`); `agent.repair` 幽灵命令 | PromptEngine.kt:252/256, MainActivity.kt:157-161, AgentTaskInbox.kt:80, hermes.md, AgentErrors.kt:22 |
| 2.7 双通道语法一致 | ❌ **静默改写** — `grep -n 关键词 文件` 经 CliInterpreter+Pipeline 变成 `[文件, --n, 关键词]`; 而系统提示词正教 Agent 用 `grep -n`/`sed -n`, CommandMonitor 也放行 | CliInterpreter.kt:44-53 → Pipeline.kt:57-59 |
| 3.7 保护链判定命中 | ❌ **双重失效** — 路径保护只挂 Pipeline(仅注册命令), Linux 通道写操作零拦截; 且 Vault 前缀写死 `com.mengpaw/mengpaw_vault`, 真实为 `com.mengpaw.shell/.../mengpaw_vault_encrypted` | IntegrityGuard.kt:275-279/40; AgentRuntime.kt:141-143 |
| 2.6 异常路径 | ❌ 中断恢复的文件提取判定集全是已删命令名 → `files` 字段恒空(功能静默失效, 测试样本恰用 `fs.write` 掩盖) | interrupted_recovery.kt:94/100 |
| 1.1/1.3 认知层 | ⚠️ 技能文档无任何幽灵引用守护; 索引文件 `plugin-index.md` 有 10 个指向不存在技能的死链 | plugin-index.md |
| 1.5 成功指引 | ❌ `agent.repair` 被当作"修复会话损坏"的指引 — 命令根本不存在, 用户按提示做必然二次失败 | AgentConversation.kt:93 |

**整改手法(可复用)**:
1. **五处同步法** — 删一个命令必须同步五处: ①实现 ②系统提示词 ③技能文档 ④工作区模板 ⑤错误/UI 文案与安全判定表;
2. **登记制** — 退役命名空间登记进守护测试的 `RETIRED_NS`, 命中即失败(带"已删说明"豁免);
3. **每个渠道一个扫描器** — 源码(含注释剥离)、技能资产、模板资产、注册表↔索引、安全表在册性;
4. **旁证发现** — 静态扫描顺带查出 `agent.repair` 幽灵、`proc.*` 表项无实现等既有缺陷。
